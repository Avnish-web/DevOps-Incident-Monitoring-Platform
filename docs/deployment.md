# Deploying to AWS

This guide takes the platform from a GitHub release to a production deployment on AWS. The same
container images that run in Docker Compose run on **ECS Fargate**. The infrastructure is defined
in Terraform (`deploy/terraform`) and applied by the `Deploy` GitHub workflow.

> Nothing in this repository creates AWS resources on its own. Every step below is run
> deliberately by an operator and costs money (see [Cost](#cost)).

## Architecture

```mermaid
flowchart TB
    user([Users]) -->|HTTPS 443| waf[AWS WAF<br/>managed rules + per-IP rate limit]
    waf --> alb[Application Load Balancer<br/>ACM certificate, HTTP→HTTPS]

    subgraph vpc[VPC 10.20.0.0/16 — two availability zones]
        subgraph public[Public subnets]
            alb
            nat[NAT gateways]
        end
        subgraph app[Private app subnets]
            web[web: Nginx + dashboard<br/>ECS Fargate ×2+]
            api[api: Spring Boot<br/>ECS Fargate ×2+]
            worker[worker: Spring Boot<br/>ECS Fargate ×2+]
        end
        subgraph data[Private data subnets — no internet route]
            rds[(RDS PostgreSQL 17<br/>Multi-AZ, encrypted, TLS forced)]
            redis[(ElastiCache Redis 7<br/>TLS + AUTH, failover replica)]
        end
    end

    alb -->|8080| web
    web -->|Service Connect 'api:8080'| api
    api --> rds
    api --> redis
    worker --> rds
    worker -->|checks, webhooks| nat --> internet([Monitored sites,<br/>Slack, SMTP])
    sm[Secrets Manager] -. injected at start .-> api & worker
    ecr[ECR] -. images .-> web & api & worker
    cw[CloudWatch logs, metrics, alarms → SNS e-mail] -. .- api & worker & web & rds & alb
```

| Concern | How it is handled |
|---------|-------------------|
| Isolation | Three subnet tiers. Databases have no internet route and accept connections only from the API/worker security groups. Tasks have no public IPs. |
| TLS | ACM certificate on the ALB (TLS 1.2/1.3 policy). `DB_SSLMODE=require` to RDS (`rds.force_ssl=1`), TLS to ElastiCache. Nginx sends HSTS because the ALB forwards `X-Forwarded-Proto: https`. |
| Secrets | The RDS master password is generated and rotated by RDS in Secrets Manager. The Redis AUTH token, alert encryption key and bootstrap admin password are generated by Terraform into Secrets Manager. ECS injects them at task start; none appear in task definitions or images. |
| Edge protection | WAF with the AWS Common, Known-Bad-Inputs and IP-Reputation rule groups, plus 2000 requests per 5 minutes per IP. Nginx and the API add their own limits behind it. |
| Availability | Two AZs; at least two tasks per service; Multi-AZ RDS; Redis replica with automatic failover; ECS deployment circuit breaker with automatic rollback; CPU-based autoscaling. |
| Migrations | Only the API runs Flyway. Terraform waits for the API service to reach a steady state (`wait_for_steady_state`) before it updates the worker, so the worker always validates against the migrated schema. |
| Observability | JSON logs in CloudWatch (30 days); Container Insights; ALB access logs in S3; VPC flow logs; alarms for ALB 5xx, unhealthy targets, **no running worker**, RDS CPU and storage, sent via SNS e-mail. |
| Supply chain | Images are built once by the Release workflow, signed with cosign, and carry SBOM and provenance. The deploy workflow copies them into ECR by digest (immutable tags), and ECR scans on push. |

### Differences from Docker Compose

| Compose | AWS |
|---------|-----|
| PostgreSQL / Redis containers | RDS / ElastiCache (managed backups, patching, failover) |
| Nginx publishes port 8080 | ALB terminates TLS in front of Nginx |
| Compose DNS name `api` | ECS Service Connect alias `api` (same Nginx config) |
| Prometheus + Grafana containers | CloudWatch metrics and alarms. The `/actuator/prometheus` endpoints still exist on the internal management ports, so Amazon Managed Prometheus (via an ADOT collector) can scrape them later without code changes. |
| Spring Session configures Redis keyspace events | ElastiCache forbids `CONFIG`, so they are set in the parameter group (`notify-keyspace-events=Egx`) and the API runs with `SESSION_REDIS_CONFIGURE_ACTION=none`. |

## Prerequisites

- An AWS account and an administrator able to run the one-time bootstrap
- A domain name and an **ACM certificate** for it in the deployment region
- Terraform ≥ 1.10 and the AWS CLI (for the bootstrap only)
- The GitHub repository with Actions enabled

## One-time setup

1. **Bootstrap** (local state; creates the state bucket and the GitHub deploy role):

   ```bash
   cd deploy/terraform/bootstrap
   terraform init
   terraform apply -var github_repository=<owner>/<repo>
   ```

   The deploy role can be assumed **only** by workflow jobs that run in the `production` environment
   of that repository (OIDC `sub` claim). No AWS access keys are stored anywhere.

2. **GitHub configuration** (Settings → Environments / Variables):
   - Create the environment **`production`** with *required reviewers*, so every deployment
     needs an approval.
   - Repository variables: `AWS_REGION`, `AWS_DEPLOY_ROLE_ARN` and `TF_STATE_BUCKET` (from the
     bootstrap outputs).
   - Provide the environment's Terraform inputs (`certificate_arn`, `admin_email`,
     `alarm_email`, SMTP settings). Either copy `terraform.tfvars.example` to `terraform.tfvars`
     in a private ops fork, or set `TF_VAR_*` environment variables on the `production` environment.

3. **E-mail alerts (optional):** create SES SMTP credentials, set `smtp_host` / `smtp_username`,
   and put the SMTP password into the generated `monitoring-production/smtp-password` secret.

## Releasing and deploying

```bash
git tag v0.1.0 && git push origin v0.1.0   # Release workflow: build, scan, sign, push to GHCR
```

Then run **Actions → Deploy → Run workflow** with `version = v0.1.0`. After approval, the workflow:

1. assumes the deploy role via OIDC;
2. copies the three release images from GHCR to ECR (all architectures, same digests);
3. runs `terraform apply -var image_tag=v0.1.0` (API first, then worker and web);
4. waits until all ECS services are stable. A failing deployment is rolled back automatically
   by the ECS circuit breaker.

**First deployment:** point your DNS record at the `alb_dns_name` output. Read the initial admin
password from the secret in `admin_password_secret_arn`, sign in, and change the password on the
**Account** page.

### Rollback

Run **Deploy** again with the previous version. Images in ECR are immutable, so the old version is
exactly what ran before. Database migrations are forward-only: before releasing a version that
changes the schema incompatibly, make sure the previous version still works with the new schema
(expand/contract migrations).

## Operations runbook

| Symptom | First checks |
|---------|--------------|
| Alarm `worker-no-running-tasks` | `aws ecs describe-services` for the worker, then its CloudWatch logs. Typical causes are a DB connectivity problem or a bad release (roll back). |
| Alarm `alb-5xx` | API logs in CloudWatch, filtered by `requestId` from the error response. Check RDS and Redis metrics. |
| Users signed out unexpectedly | ElastiCache failover or restart. Sessions live only in Redis, so this is expected and harmless. |
| Alerts not delivered | Alert channel history on the dashboard's **Alerts** page (status and last error), then the worker logs. |
| Database storage alarm | Storage autoscaling grows up to `db_max_storage_gb`. Check `RETENTION_CHECK_RESULTS_DAYS`. |

## Cost

Rough on-demand prices in `eu-central-1`, per month:

| Setup | Main components | Approx. cost |
|-------|-----------------|--------------|
| Production defaults | 2 NAT GW, ALB, WAF, 6 Fargate tasks (ARM), RDS `db.t4g.small` Multi-AZ, ElastiCache 2× `cache.t4g.micro` | ~ USD 250–300 |
| Demo (`single_nat_gateway=true`, `db_multi_az=false`, `redis_replicas=0`, 1 task per service) | 1 NAT GW, ALB, WAF, 3 Fargate tasks, single-AZ RDS and Redis | ~ USD 110–140 |

NAT gateways, the ALB and RDS dominate. Destroy a demo environment with `terraform destroy` after
setting `deletion_protection = false`.
